---
title: Workflows and schedules
description: Turn a repeatable job into ordered steps and run it manually, on a schedule, or from an event.
---

A Workflow defines a reusable job. Each step has instructions and a model configuration, and can
use installed Skills. Every invocation creates a Task with its own progress and result.

Open **Workflows** from the sidebar, or create a simple Workflow directly in Chat.

## Create and manage from Chat

Workflow tools in Chat are currently available to workspace admins. Describe the job and when it should run:

> Every Friday at 09:00 Europe/Berlin, check Dia’s changelog for accessibility API changes.
> Remember which releases have already been checked.

Chat creates a personal Workflow, enables memory for the cross-run state, and confirms its status,
schedule, next run, and link. A clear request for scheduled or recurring work activates it once
the timing is complete. If you only say “weekly,” the agent asks for the missing day and time.
Ask for a draft when you want to save an idea without turning it on.

You can also ask Chat to inspect, rename, edit, activate, pause, run, or archive a Workflow.
Pausing preserves its definition and history. Turning memory off preserves its contents;
clearing memory requires a separate explicit request. New Workflows are personal unless you
ask to share them with the company.

Chat initially authors one-step Workflows with a manual trigger or one schedule. Use the editor
for multiple steps, event triggers, model settings, and Slack channel controls. Chat preserves
those settings when making other edits to existing Workflows. Background Tasks cannot author
or start other Workflows.

## Create in the editor

1. Open **Workflows** and select **New workflow**.
2. Give it a name and description that identify the job, such as `release-review`.
3. Start with a **Manual** trigger.
4. Write the first step's instructions. Choose its model and any Skills it needs.
5. Use **Add step** when the next part needs a distinct handoff or model.
6. Wait for the save indicator, then set the Workflow to **Active** when it is ready to run.

Keep each step's output explicit. For a release review, two steps could be:

| Step | Instructions |
| --- | --- |
| Gather evidence | Read the supplied release scope, linked GitHub PRs, and test results. Produce an evidence list with source links and unanswered questions. |
| Write the review | Use the evidence from the previous step to write a release recommendation. Separate verified checks from missing evidence. Return the review for a person to approve. |

Include the needed context or artifact in the handoff. A later step should be able to understand
what to do from its instructions, the task request, and the previous step's output.

## Run it from Chat

Type `#` in Chat, select an active Workflow, and add the request for this invocation:

```text
#release-review Review the release in OWNER/REPO from v1.2.0 to v1.3.0.
Use the linked test report and list anything that still needs verification.
```

Selecting a Workflow shows its saved model settings in the composer. For workflows with multiple
steps, each step has its own controls. Change a model or reasoning effort to override it for
**this run only**, or select **Reset** to return to the Workflow defaults. These changes do not
update the saved Workflow or your usual Chat model. Image and PDF uploads are checked against
the models selected for the Workflow. Removing the hashtag restores the normal Chat controls.

The work appears in **Tasks**. Inspect one complete run and refine the instructions before
scheduling it. Editing a Workflow doesn't rewrite the definition captured by an existing Task.

## Run on a schedule

In **Trigger**, choose **On a schedule**. Set the frequency and timezone, then fill in the
**Task request** with context that will make sense at each invocation. For a weekly update, use
“the previous seven days” instead of a fixed date range.

The schedule stores a cron expression and timezone. Check both before relying on a local-time
routine. A scheduled Workflow also has **Run now** so you can test it immediately after saving.
Set the Workflow back to **Draft** to stop automatic invocation while you revise it. Previously
created Tasks keep their own status and history.

You can also create a scheduled Workflow in Chat. Specify the day, time, and timezone, and
check the confirmed next run. Scheduled work uses the same Workflows you see in the editor.

## Run from a Plugin event

1. Install and connect the **Linear** Plugin.
2. On its Plugin page, enable the event you want for the current workspace.
3. In the Workflow, choose **On an event**.
4. Select the available event, connected account, and team, then write the **Task request**.
5. Save and activate the Workflow.

The current Linear Plugin supports **Issue created**. The event choices come from the installed
Plugin version and its enabled events. Existing **issue enters triage** triggers may also appear;
those require a team with Triage enabled. If the event option is unavailable, follow the editor's
link to connect Linear or enable an event.

Event delivery starts background work. Ensure the account has access and the needed tools are
enabled before relying on an event-driven Workflow.

## Plan for unattended work

Tasks don't have a person answering each tool prompt. Keep the job within its available permissions,
and have it return a concrete draft or question if it reaches a decision that needs you. See
[Permissions](/docs/core-concepts/integrations#background-and-coding-work) and
[Troubleshooting](/docs/guides/troubleshooting).
