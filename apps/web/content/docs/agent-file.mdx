## The whole thing in one screen

An `.agent` file has two parts: a short header with metadata, and a body of instructions you write in plain English.

```yaml
---
title: "Fundraising copilot"
model: openai/gpt-5.4
tools:
  - exa
brain:
  - /
  - docs/README.md
agents:
  - path: agents/sales-research.agent
    name: Sales research
integrations:
  github:
    repositories:
      - id: opencompany-web
        fullName: opencompany/web
        defaultBranch: main
---

Research investors with @exa. Write careful thesis summaries. Read @brain/ first. Ask @agent/sales-research for account notes. Work in @opencompany/web with @amp.
```

That's it. The `---` lines fence off the header. Everything below is what the AI model reads as instructions.

## The header

The header is YAML — a simple `key: value` format. These are the main fields.

### `title`

The name of the agent. Used in the sidebar, in URLs, and as a hint to the model about what its job is.

```yaml
title: "Fundraising copilot"
```

If you leave it empty, opencompany fills in `"Untitled agent"` so the file is always valid.

### `tools`

A list of capabilities the agent can use beyond text generation. A simple tool
can be written as a string. A tool with persisted configuration is written as an
object.

```yaml
tools:
  - exa
  - id: amp
    type: coding_agent
    provider: amp
    prCapable: true
```

Attaching a GitHub repository (via `integrations.github.repositories`) is what grants
repository access — not the `amp` tool. Any agent with an attached repository gets
repo-scoped `git`/`gh` credentials in the `shell` tool plus a dedicated `gh` tool, and
can clone on demand into `work/`. `amp` is just one consumer of attached repositories;
when more than one is attached, pass the target to `amp_coder` via its `repository`
argument.

| ID | What it does |
| --- | --- |
| `exa` | Web research with search, content extraction, people lookup, and cited answers. |
| `amp` | Coding work delegated into a sandboxed runtime, operating on an attached repository. |
| `linear` | Workspace MCP access to Linear issues, projects, and comments. |
| `slack` | Workspace MCP access to Slack search, messages, files, emoji, and users. |

Unknown tool names are silently ignored, so adding a tool that doesn't exist yet won't break the file. Tool labels, descriptions, and runtime function names come from the platform catalog, not from this file.

### `brain`

A list of long-lived context files or folders the agent can access in a session.

```yaml
brain:
  - /
  - docs/README.md
  - product/
```

These paths live under `brain/` in the workspace repo. Use `/` to mount the whole Brain root. File paths mount one file. Folder paths end in `/` and mount matching files below that folder.

### `agents`

A list of other agents in the same workspace that this agent can delegate work to.

```yaml
agents:
  - path: agents/sales-research.agent
    name: Sales research
```

The body mention is `@agent/<slug>`, where `<slug>` is the filename without `agents/` or `.agent`. During a run, these references expose a delegation tool. The child agent runs in an inspectable child session hidden from sidebar history, and its answer is returned to the parent as a tool result.
The result also includes `childSessionId`; passing that id back as `sessionId` with a new prompt continues the same delegated child session.

### `integrations.github.repositories`

A list of workspace-authorized GitHub repositories referenced by the body.

```yaml
integrations:
  github:
    repositories:
      - id: opencompany-web
        fullName: opencompany/web
        defaultBranch: main
        binding:
          provider: github
          resourceType: repository
          externalId: "123456789"
          displayName: opencompany/web
          connection:
            externalId: "987654"
            label: OpenCompany
            accountName: opencompany
            accountType: Organization
```

`fullName` remains the readable reference shown in body mentions. `binding` is optional normalized runtime data that identifies the concrete provider resource and parent connection without making opaque database IDs part of the human-authored reference. Unknown or unauthorized repository mentions stay in the body as text, but they do not contribute to the saved config.

## The body

The body is plain Markdown. Whatever you write here, the model reads as its instructions. Treat it like an SOP for a new hire: describe the outcome, the constraints, and the style.

A good body says:

- **What success looks like.** "Return one paragraph per fund." "Always include a source link."
- **What to avoid.** "Don't include funds with fewer than three investments this year."
- **Who the output is for.** "Write for a founder reading on their phone."

There's no length limit, but shorter is usually better. If the instructions are getting long, that's often a sign the agent should be two agents.

## Mentions

Inside the body you can write `@something` to attach a tool, Brain path, workspace agent, or GitHub repository. opencompany reads these mentions out of the body and uses them to fill in those header fields — so the body is the source of truth for tools and context. The model is explicit per-agent config in the header.

```text
Find investors with @exa.        ← tool: exa
Read @brain/product/ first.      ← Brain folder
Work in @opencompany/web.        ← GitHub repository
Read @brain/ first.              ← Brain root folder
Ask @agent/sales-research.       ← workspace agent
```

This is what mentions can be:

- A tool ID, like `@exa`
- A Brain path, like `@brain/`, `@brain/docs/README.md`, or `@brain/product/`
- A workspace agent, like `@agent/sales-research`
- A GitHub `owner/repo`, like `@opencompany/web`

If you write `@something` that doesn't match anything, opencompany leaves it as plain text. It won't error, but it also won't do anything special.

### After-session memory

Add `#after-session` to run a background memory pass after a session has been idle for 3 minutes:

```text
Help with customer calls. #after-session Update @brain/memory.md with durable preferences and decisions from the transcript.
```

The hook prompt is the text after the first `#after-session` marker through the end of that paragraph. It does not create a visible chat message; it reuses the agent loop and can update mounted Brain files when there is useful long-lived context to save.

### Tiptap content is not the contract

The web editor stores Tiptap JSON so mentions can render as chips when you reopen an agent. That JSON is only a presentation cache. The `.agent` body text is the contract, and mention-backed runtime config is derived from the body text that will be written to GitHub.

If body text and Tiptap JSON ever disagree, the body wins. This keeps stale editor state from removing repository bindings or tool config during a save.

## Saving and syncing

When you save an agent:

1. The change is stored immediately. Refresh, close the tab, do whatever — your edit is safe.
2. A few seconds later, opencompany commits the file to your workspace's GitHub repo.
3. If the commit fails for any reason (rare), you'll see a warning on the agent's row. Your work is still saved; only the GitHub copy is behind.

You can also edit the file directly in GitHub or in your local editor. The next time opencompany reads from the repo, your changes show up.

## Where files live

In your workspace's GitHub repo, agents live under `agents/`:

```text
your-workspace-repo/
├── agents/
│   ├── fundraising-copilot.agent
│   ├── ops-triage.agent
│   └── sales-research.agent
└── brain/
    ├── docs/README.md
    └── product/positioning.md
```

The filename comes from the title — lowercased, with spaces turned into dashes. Rename the title, and the next save will use the new filename.

## Examples

### A small one

```yaml
---
title: "Notes"
model: openai/gpt-5.4-mini
tools: []
---

Summarize whatever I paste below in three bullets. Skip preamble.
```

### A research agent

```yaml
---
title: "Investor research"
model: openai/gpt-5.4
tools:
  - exa
---

Find investors active in seed-stage developer tools. For each fund:

- Use @exa to find their most recent investment in the space.
- Write one paragraph covering thesis, typical check size, and that recent
  investment.
- Include a link to one primary source per fund.

Skip funds that haven't made an investment in the last 12 months.
```

### One where mentions do the work

You can write only the instructions and let opencompany figure out the header:

```yaml
---
title: "Research"
model: openai/gpt-5.4-mini
tools:
  - exa
---

Find investors with @exa. Write a concise brief before sending.
```

After saving, the header above is what ends up in the file — even though you only wrote the body. The `@exa` mention added the tool. The model remains explicit per-agent config.

### A coding agent for a repo

```yaml
---
title: "Web code reviewer"
model: openai/gpt-5.4-mini
tools:
  - id: amp
    type: coding_agent
    provider: amp
    prCapable: true
integrations:
  github:
    repositories:
      - id: opencompany-web
        fullName: opencompany/web
        defaultBranch: main
---

Review pull request context in @opencompany/web and use @amp for implementation work.
```

## How forgiving the format is

You don't need to be careful with this file. The parser is built to never reject what you wrote.

- Missing header? Treated as a body with default settings.
- Unknown model name? Falls back to the default.
- Unknown tool name? Dropped.
- Weird whitespace or line endings? Cleaned up automatically.

The goal is that you can write what's in your head, save, and trust that the file is valid.

## Questions

**Can I write `.agent` files by hand and commit them?**
Yes. Push them to your workspace's GitHub repo, then trigger an import from the app. opencompany reads the format the same way no matter who wrote it.

**Can two people edit the same agent at the same time?**
Yes, but the last save wins for now. We're working on something better. In the meantime, if you're collaborating on a complex agent, it's worth coordinating.

**How do I add a new model or tool?**
That requires a code change — we ship a curated catalog so every workspace knows the same set of models and tools work. Open a request and we'll prioritize.

Tool availability is static for now: every workspace can use every supported catalog tool. The runtime catalog records each tool's default enabled state, platform env requirements, and required workspace resource type when applicable, so future admin controls can use catalog defaults without changing `.agent` files.
