1. The model loop

The main chat is a single-model, multi-step agent loop built on the Vercel AI SDK's streamText, served from a Next.js route handler at apps/goat/app/api/chat/route.ts. One POST = one user turn. Within that turn the model can take up to 8 steps (OPENCOMPANY_CHAT_MAX_STEPS) — each step being a model generation that may call tools, with tool results fed back in for the next step.

1 · AUTH & VALIDATE Gate the request
Resolve the Goat user + workspace (currentGoatUser). Parse the message, attachments (image/PDF capability checked per model), model id (unknown ids fall back to the default), and session id. Max prompt length: 10,000 chars. If credits enforcement is on and the workspace balance is ≤ 0, return 402 before any model call (fails open on a balance-read error).
2 · PERSIST USER TURN Store the message, load history
createGoatChatUserTurn finds or creates the session, loads all prior messages of the session (no truncation/windowing — the full session history goes to the model), appends the new user message, and kicks off async title generation. Docx/xlsx attachment text is extracted once at submit time and stored.
3 · ASSEMBLE CONTEXT Build system prompt + tools
createOpenCompanyChatSystemPrompt composes the prompt from five XML-tagged blocks (see §3). createOpenCompanyChatToolContext wires up 1–7 tools depending on the user's role and feature flags (see §4).
4 · GENERATE streamText agent loop
Model is resolved through the Vercel AI Gateway (createGateway + VERCEL_AI_GATEWAY_API_KEY) with per-user/per-feature attribution headers. stopWhen: stepCountIs(8) caps the tool loop. smoothStream() re-chunks provider token bursts into word-level streaming. Tool executors run server-side inside this loop.
5 · STREAM TO CLIENT Resumable UI message stream
The response is a UI message stream (SSE). When Redis-backed resume is enabled, a server-side copy of the stream keeps generation alive across browser disconnects; explicit "stop" arrives via a Redis stop signal that aborts the generation controller. Without Redis, a client disconnect cancels generation.
6 · FINISH Persist, bill, observe
On finish: persist the assistant message (with a debug trace of tool calls/results, finish reason, and last-step token usage that drives the context meter), compute model cost from usage and debit workspace credits (idempotent per user message), and emit OpenTelemetry spans/metrics for the turn.
Engine detour: if the user @-mentions the codex engine (and has Codex connected), the turn is flagged requestedEngine: "codex" — tool context then forces start_task to spawn a Codex-engine task, and the turn is exempt from credit checks (the user's own Codex auth pays). Attachments are rejected for engine turns.

The model is stored per chat session. Attachment support (images, PDF) is checked per model before accepting a message. Gateway calls carry attribution provider-options (hashed user id, feature = chat, session id, brain ref) for cost accounting and observability.

3. System prompt anatomy

Defined in apps/goat/lib/prompts/main-chat.ts. The prompt is assembled per request from five XML-tagged blocks, joined by blank lines. Several lines are conditionally included based on the user's role and available integrations — so different users literally get different prompts.

Block 1 — <system> · identity

You are OpenCompany, the main agent for getting work done and building the user's agentic company.
You run in the main app as a chat interface. The rest of the app is organized around tasks: durable
work items that can be spawned from this main agent when useful, tracked in Tasks, and executed by
more specialized agents.

The second sentence only appears when task tools are enabled for the user.

Block 2 — <runtime_context> · dynamic state

  • Current date — ISO date (YYYY-MM-DD).
  • Active brain — one of three variants: no brain available ("goat_brain will fail"), read-only access ("browse-only: do not save, capture, or otherwise add Brain content"), or full access (names the brain + workspace and explains that save_to_brain feeds the background curation agent).
  • Recurring schedules — up to 20 of the user's schedules, one line each: id, name, cron, timezone, enabled, nextRunAt. This is what lets the model resolve "cancel my Monday digest" to a concrete schedule id. Shows "none" when empty; omitted entirely when schedule tools are off.

Block 3 — <user_context> · profile

This is the user's compact user.md-style profile from the database.
Use it as durable personal context. Do not invent missing profile fields.
firstName="Louis"  lastName="…"  email="…"  timezone="Europe/Berlin"

Falls back to "User profile context is unavailable. Do not infer the user's name, email, or timezone from chat history."

Block 4 — <behavior> · the operating rules

The largest block (~19 lines). Key themes, with their gating:

Block 5 — <soul> · persona

Be a proactive, founder-focused operator: direct, practical, and biased toward forward motion.
Think like a sharp chief of staff for an early company. Clarify only when it materially changes
the work; otherwise make the best reasonable assumption and move.
Protect the user's time. Surface the decision, next action, or tradeoff plainly. Prefer crisp
execution over commentary.
Care about leverage: turn vague intent into useful work, preserve context for the future, and
help the company compound its operating knowledge.

4. Tool surface

Up to seven tools, built in createOpenCompanyChatToolContext (lib/chat-agent.ts) with descriptions centralized in lib/prompts/tool-descriptions.ts. Only goat_brain is unconditional; everything else is wired per-request based on role and config.

goat_brain always registered

"Read-only access to the user's durable Goat Brain (structured memory stored as Markdown files). Use it to recall and inspect existing knowledge, never to write. Use query for recall/search, list for inventory, get for a known brain id, timeline for a record's history, help for command-specific usage, and doctor for validation. … To add or edit Brain content — new pages, evidence, corrections, links, or merges — use save_to_brain instead; the background curation agent files it. Do not treat Brain as a chat scratchpad."

Shape: CLI-shaped tool. The executor runs the brain CLI scoped to the workspace's active brain; fails gracefully when no brain is accessible.
  • commandreq — enum: query · list · get · timeline · doctor · help
  • flags — CLI flags without dashes; since accepts 6h/2d/1w or ISO timestamps
  • stdin — optional, rarely needed for reads
save_to_brain workspace admins only

"Save something the user wants remembered — a reference, idea, thought, note, decision, pasted content, or an attached file — into their Brain. This captures the content as a draft page in the inbox immediately and queues a background curation agent that files it properly (title, type, folder, links to related pages). … Do not rewrite or summarize the content; capture what the user gave you."

Shape: the only write path in chat — everything else (rewrite, merge, link, delete) belongs to the durable ingestion agent in the runner worker.
  • content — verbatim or lightly cleaned; omit when saving attachments
  • title — optional; derived from content if omitted
  • intent — optional one-liner to help the curation agent file it
  • attachmentIds — saves conversation attachments as Brain assets
start_task taskSpawningEnabled + admin

"Start a task when the user's request should become an asynchronous tracked task, including work that needs connected-account context, external research, monitoring, or a specialized just-in-time agent. If the user explicitly asks for Codex … preserve that execution intent by setting engine to codex."

Shape: spawns a durable Goat task run by a specialized agent, using the same model as the chat session.
  • promptreq — brief; the user's own request as backbone, no invented plans
  • namereq — 2–7 word task name
  • reason — why a task instead of a chat answer
  • engine — opencompany | codex; also inferred from the user's message text ("codex" mentions, with negation detection)
schedule_task taskSpawningEnabled + admin

"Create a recurring Goat task schedule from the user's request. Use only when the user clearly asks for repeated, recurring, scheduled, or cron-like work. Convert the recurrence to a valid 5-field cron expression and save directly; if the recurrence is ambiguous or not cron-expressible, ask a short follow-up instead of calling this tool."

  • promptreq · namereq · cronreq (5-field, no seconds)
  • timezone — IANA; defaults to the user's saved timezone
  • sourceDescription — natural-language recurrence ("every weekday at 9 AM")
  • reason
edit_task_schedule taskSpawningEnabled + admin

"Edit an existing recurring Goat task schedule. … Identify the schedule by id when known, otherwise by its unique visible name from runtime context. If the target is unclear, ask a short follow-up instead of calling this tool."

  • scheduleId (preferred) or scheduleName (unique-name lookup, normalized case/whitespace; ambiguous matches return an error asking which one)
  • name · prompt · cron · timezone · sourceDescription · reason — all optional; unset fields keep current values
delete_task_schedule taskSpawningEnabled + admin

"Delete an existing recurring Goat task schedule so it no longer creates future task runs. Already-created queued or running task runs continue."

  • scheduleId or scheduleName · reason
web_search EXA_API_KEY set

"Search the public web once for simple freshness-sensitive questions. Use this for one-shot current facts, recent updates, or latest docs. Do not use it for deep research, monitoring, multi-source reports, connected-account work, or anything that should become a tracked task."

Shape: Exa "fast" search, 5 results with highlights; cost tracked in micros per search.
  • queryreq — concise; entity names + the requested fact
  • recencyDays — 7 | 30 | 90 freshness window

5. In-loop guardrails

Beyond prompt instructions, the tool executors enforce hard limits in code:

GuardrailMechanism
Max 8 steps per turnstopWhen: stepCountIs(OPENCOMPANY_CHAT_MAX_STEPS) ends the tool loop
One web search per turnSecond web_search call returns an error telling the model to start a task for deeper research
One task per turnRepeat start_task calls return the first task with status: "already_started"; in-flight calls are awaited, not duplicated
One schedule per turnSame idempotency pattern for schedule_task
Dedup savessave_to_brain keyed on title+content+attachments; duplicates return status: "already_captured" instead of minting another inbox draft
Brain writes impossibleChat only exposes the read command enum; all writes route through the durable curation agent via save_to_brain
Engine overrideAn explicit @codex mention forces the task engine regardless of what the model passes

6. Streaming, persistence & billing

Resumable streams

With Redis configured, generation is decoupled from the client connection: a server-side copy of the SSE stream (registered via consumeSseStream + after()) drives the turn to completion even if the browser refreshes or closes. The client can reattach to the active stream. Explicit stop is a Redis signal that aborts the generation controller. Without Redis, disconnect = cancel.

Persistence & debug trace

The assistant message is persisted in onFinish with a debugTrace (opencompany.chat.debug.v1): model, finish reason, UI message parts, all tool calls/results across steps, duration, and the last step's token usage — which approximates context-window fullness and drives the chat header's context meter. If the stream dies mid-turn but a task was started or tools visibly ran, a fallback assistant message is persisted so the UI isn't left dangling.

Billing

Chat is usage-based on all plans. A turn can't start on an empty credit balance (402, fails open on read errors). After generation, cost is computed from gateway token usage (input, output, cache read/write) plus a platform fee, and debited idempotently per user message (chat:<userMessageId>) so stream resume/replay can't double-charge. Unknown-priced models debit nothing. Codex-engine turns skip billing entirely. A debit failure never fails the turn.

Observability

Every turn opens a goat.chat_turn span with hashed user id, model, session/message ids, task-started flags, web-search cost/results, outcome (success/failure/aborted), and failure category; metrics cover turn duration, tasks started, web searches and their cost, and model cost in USD micros.
